# Peer Review — Story 00000027: Add diagonal flags

## Summary

The branch adds a rule-configuration model (`ruleFlags.ts` + `configuration.ts`)
for the two proposed diagonal-attack flags, threads a required
`RuleConfiguration` through `legalAttacks`/`hasAnyLegalPly`/`computeOutcome` and
every game-state artifact in place of the bare `Edition`, implements both flags
in `legalAttacks`' diagonal loop, renders and parses the `Ruleset` stamp, offers
both choices on the new-game screen, and surfaces a record's rules while
reviewing (including tokens this app cannot resolve). The threading is complete
and compiler-driven — no `legalAttacks` call site was left on a default — and the
default path is demonstrably untouched: no existing record fixture, tag string or
position block was edited, and the flag logic is confined to the diagonal loop
with `combat.ts`/`outcome.ts`/`replay.ts` unchanged, as the plan predicted. The
plan does include a step covering `README.md` (Decision 12 / Step 11), and it was
carried out.

Automated checks from the repository root: **`npm run typecheck` — clean**;
**`npm run lint` — clean**; **`npm test` — 31 files, 707 tests, all passing**. No
findings arise from any of the three.

The findings below are mostly about the newest, least-settled area (Step 10's
unrecognised-token handling) and about documentation drift between `story.md` and
what shipped. Nothing found is a correctness bug in the rules themselves: the
flank geometry, the composition of the two flags, the "skirt" survival, the
canonicalization property and the stamp ordering all check out against the
companion project's specification, and the two design calls flagged for scrutiny
are addressed as comments #1 (repeated tokens) and, in passing, #1's note on
malformed tokens.
